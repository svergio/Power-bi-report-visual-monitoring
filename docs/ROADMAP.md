# Дорожная карта развития платформы мониторинга визуальных регрессий BI-систем (ROADMAP)

## Аннотация и стратегическая цель

Данный документ представляет собой стратегический план технологического и продуктового развития проекта мониторинга отчетов. Текущая версия системы (`pbimonitor`) представляет собой специализированный инструмент регрессионного тестирования верстки Power BI Report Server и опубликованных отчетов Power BI. 

**Стратегическая цель владельца продукта:** трансформировать узкоспециализированный монитор в **универсальную платформу сквозного визуального контроля и наблюдаемости (Visual Regression & Observability Platform) для любых корпоративных BI-систем**. Платформа проектируется с учетом строгих требований энтерпрайз- и бигтех-эксплуатации (высокая надежность, распределенная горизонтально масштабируемая архитектура, безопасность, SSO, наблюдаемость), а также критериев включения в **Единый реестр российских программ для электронных вычислительных машин и баз данных (Реестр отечественного ПО Минцифры России)**.

## 1. Поддержка BI-систем через адаптеры

### 1.1. Архитектура адаптера (BI Adapter Pattern)

Текущая реализация жестко завязана на Power BI: класс `SeleniumClient` в `src/pbimonitor/infrastructure/selenium/client.py` напрямую содержит эвристики ожидания Power BI (поиск iframe, спиннеров `.spinner, .loading`, базовая HTTP-аутентификация в URL и проверка ключевых слов `login`/`signin` в URL).

Для превращения системы в универсальную платформу внедряется унифицированный интерфейс адаптера BI-системы (`BIAdapter`) и фабрика адаптеров (`BIAdapterRegistry` / `BIAdapterFactory`).

                                          |

                              +-----------------------+
                              |   BIAdapterFactory    |
                              +-----------+-----------+
                                          |
                   +----------------------+----------------------+
                   |                                             |

        |   PlaywrightClient |                        |    SeleniumClient  |
        +----------+---------+                        +----------+---------+
                   ^                                             ^
                   +----------------------+----------------------+
                                          |
                                          v
                              +-----------------------+

#### Базовый контракт адаптера (`BaseBIAdapter`)

Интерфейс адаптера разделяется на пять ключевых обязанностей:

```python
from abc import ABC, abstractmethod
from typing import Any, Dict, List, Optional, Tuple
from dataclasses import dataclass
from pathlib import Path

@dataclass(frozen=True)
class TargetVisual:
    visual_id: str
    name: str
    bounding_box: Tuple[int, int, int, int]  # x, y, width, height
    css_selector: Optional[str] = None
    is_kpi: bool = False

@dataclass
class AuthContext:
    auth_type: str  # basic, oauth2_token, session_cookie, kerberos, jwt, api_key
    credentials: Dict[str, Any]
    session_storage: Optional[Dict[str, str]] = None
    cookies: Optional[List[Dict[str, Any]]] = None
    headers: Optional[Dict[str, str]] = None

class BaseBIAdapter(ABC):
    @property
    @abstractmethod
    def bi_type(self) -> str:
        """Идентификатор BI-системы (например, 'datalens', 'visiology3', 'superset')."""
        pass

    @abstractmethod
    def authenticate(self, browser_session: Any, auth_ctx: AuthContext) -> None:
        """
        Выполнение аутентификации в BI-системе:
        - Ввод учетных данных в форму SSO/LDAP
        - Инъекция токенов Bearer/JWT в LocalStorage/SessionStorage
        - Установка сессионных cookie
        - Перехват и повторная авторизация при 401/403
        """
        pass

    @abstractmethod
    def navigate_to_report(self, browser_session: Any, report_url: str, params: Optional[Dict[str, Any]] = None) -> None:
        """
        Переход по URL отчета/дашборда с передачей параметров:
        - Открытие нужной вкладки/страницы дашборда
        - Установка режима просмотра (kiosk/embed/fullscreen)
        - Передача параметров в URL / query parameters
        """
        pass

    @abstractmethod
    def wait_for_data_loaded(self, browser_session: Any, timeout_seconds: int = 60) -> bool:
        """
        Детерминированное ожидание завершения рендеринга всех визуалов:
        - Исчезновение специфичных для BI спиннеров и скелетонов
        - Ожидание сетевого затишья (networkidle: нет активных XHR/Fetch запросов к аналитическому бэкенду > 500ms)
        - Проверка флагов готовности в JS-контексте страницы (window.BI_READY, data-state='loaded')
        """
        pass

    @abstractmethod
    def apply_filters(self, browser_session: Any, filters: Dict[str, Any]) -> None:
        """
        Установка параметров фильтрации (селекторы, периоды дат, срезы):
        - Через URL-параметры (предпочтительно для детерминизма)
        - Через взаимодействие с UI селекторов (клик, выбор значения)
        - Через JS API встраивания (если доступно в BI)
        """
        pass

    @abstractmethod
    def locate_visuals(self, browser_session: Any) -> List[TargetVisual]:
        """
        Сегментация дашборда на отдельные визуализации:
        - Поиск контейнеров графиков/таблиц/KPI через специализированные CSS/DOM-селекторы
        - Определение координат bounding box каждого визуала для поблочного diff
        """
        pass

    @abstractmethod
    def detect_render_errors(self, browser_session: Any) -> List[str]:
        """
        Поиск явных ошибок рендеринга на стороне BI:
        - 'Query failed', 'Data source error', 'No data', плашки сбоя коннектора
        - HTTP 500 в фоновых запросах к датасетам
        """
        pass
```

## 2. Доработка ядра алгоритма визуального сравнения и слой VLM

Текущий алгоритм:
- Перцептивный хеш `dhash` (размер 8x8, `ImageHash`) для грубого отпечатка.
- Рекурсивный квадродерево-поиск (`quadtree`) на основе MSE (Mean Squared Error) для блоков пикселей.
- Побайтовое XOR-сжатие через `np.bitwise_xor` и `gzip`.

### 2.1. Снижение ложных срабатываний (False Positives)

В реальных отчетах плоские пиксельные сравнения приводят к лавине ложных алертов из-за:
- Динамических меток времени («Данные обновлены в 14:35:01», бегущие строки);
- Анимации прогресс-баров и графиков при старте;
- Размытия шрифтов (subpixel text antialiasing при разных версиях браузера/видеокарты);
- Мерцания и сдвига на 1-2 пикселя графических примитивов.

#### Инженерные решения:

1. **Многоуровневое маскирование динамических зон (Masking Engine):**
   - **Статические координаты (Coordinate Masking):** задание зон игнорирования `(x, y, width, height)` в конфигурации отчета.
   - **DOM/CSS-селекторное маскирование (Selector Masking):** возможность указать CSS-селекторы (например, `.report-timestamp`, `.live-ticker`, `[data-testid='current-time']`). Браузерный агент перед снятием скриншота программно скрывает (`visibility: hidden`) или заливает черным цветом данные элементы через инъекцию JavaScript/CSS.
   - **Автоматическое динамическое маскирование (Auto-masking):** снятие серии быстрых кадров (2-3 снимка с интервалом в 500 мс); зоны с меняющимися пикселями автоматически помечаются как динамические и маскируются.

2. **Переход от наивного MSE к структурному сходству (SSIM):**
   - MSE чувствителен к равномерному изменению яркости на 1 единицу или субпиксельному сглаживанию шрифтов.
   - Внедрение **SSIM (Structural Similarity Index Measure)** и **MS-SSIM (Multi-Scale SSIM)** через оптимизированные C-расширения (`scikit-image` / `OpenCV`).
   - Сравнение контраста, структуры и яркости независимо, что отсекает шум антиалиасинга.

3. **Покомпонентный diff по отдельным визуалам (Visual-level diffing):**
   - Вместо монолитного скриншота 1920x1080 адаптер вырезает bounding box каждого виджета.
   - Сравнение выполняется изолированно по виджетам. В лог и базу сохраняется результат вида: «Виджет "Выручка" — 0% diff; Виджет "Динамика продаж" — 12% diff».

4. **Детекция пустых визуалов и системных ошибок (Error Banner & Empty State Detection):**
   - Встроенные детекторы аномалий: проверка на однородный белый/серый блок в зоне визуала (признак не загрузившегося чарта).
   - Детекция стандартных надписей об ошибках («Ошибка загрузки данных», «Не удалось подключиться к серверу», «Query timeout expired») через эвристики DOM и OCR.

5. **OCR-валидация критических KPI (Optical Character Recognition):**
   - Извлечение ключевых числовых значений из плиток KPI с помощью легковесного локального движка **Tesseract OCR / Fast-PaddleOCR**.
   - Бизнес-правило: если пиксели изменились, но числовое значение KPI осталось в пределах допустимого диапазона (или равно эталонному), статус классифицируется как `visual_layout_drift`, а не критический `data_anomaly`.

### 2.2. Слой визуально-языковых моделей (VLM / Local Vision-Language Models)

В случаях, когда алгоритмический diff (SSIM / Quadtree) зафиксировал отличие, превышающее порог, запускается интеллектуальный арбитраж на базе Vision-Language моделей (VLM).

#### Архитектура и условия вызова VLM (Триггеры):
1. **Спорная зона (Gray Zone):** процент изменений $0.5\% \le \text{diff\_percent} \le 5.0\%$, когда алгоритмически невозможно отличить полезное изменение (обновилась цифра в таблице) от артефакта (чуть сдвинулась координатная сетка).
2. **Подозрение на ошибку:** резкое падение энтропии изображения (исчез сложный график, появилась серая плашка).
3. **Критичные отчеты (Tier-0 Dashboards):** дашборды топ-менеджмента, где ложные алерты недопустимы.

```
+--------------------------------------------------------------------------------+
|                        Check Execution Pipeline                                |
+--------------------------------------------------------------------------------+
                                       |
                                       v
               +-----------------------------------------------+
               |    SSIM / Visual-Level Diff / OCR Detection   |
               +-----------------------------------------------+
                                       |
                     +-----------------+-----------------+
                     |                                   |
         diff_percent == 0                  diff_percent > Threshold
                     |                                   |
                     v                                   v
             [ UNCHANGED ]                     [ Gray Zone / Anomaly ]
                                                         |
                                                         v
                                       +-----------------------------------+
                                       | VLM Gateway (Triton / vLLM / Ollama)
                                       +-----------------------------------+
                                                         |
                                                         v
                                       +-----------------------------------+
                                       | Local Open Weights Model          |
                                       | (Qwen2-VL-7B / Vikhr-Gemma / etc.)|
                                       +-----------------------------------+
                                                         |
                                                         v
                                           Структурированный JSON-вердикт
```

#### Модели для импортозамещения и Реестра отечественного ПО:
Использование зарубежных проприетарных облачных API (OpenAI GPT-4o, Google Gemini, Anthropic Claude) **категорически исключено**, так как это прямо противоречит требованиям информационной безопасности КИИ, 152-ФЗ и правилам Реестра Минцифры.

Стек локального исполнения (On-Premises AI):
- **Модели:**
  - `Qwen2-VL-7B-Instruct` / `Qwen2.5-VL-7B` (Apache 2.0, выдающееся качество распознавания элементов UI, графиков, таблиц и чисел);
  - `MiniCPM-V-2.6` (высочайшая энергоэффективность, квантование INT4, возможность работы на скромных GPU);
  - `Vikhr-Gemma-2B / VLM` (отечественные адаптации открытых весов с улучшенным русскоязычным пониманием контекста).
- **Среда инференса:** `vLLM` или `Triton Inference Server` с развертыванием в закрытом периметре (On-premise GPU-кластер, карты NVIDIA A100/A30/L40S или отечественные ускорители на базе НТЦ «Модуль»/ПК при поддержке драйверов).

#### Контракт и формат вердикта (VLM JSON Schema):

Промпт требует от модели строгого анализа двух изображений (Baseline и Current) и сгенерированной тепловой карты различий (Diff overlay).

#### Оценка стоимости и аппаратных ресурсов:
- **Облачные API:** 0 руб. (не используются).
- **On-premise инференс:**
  - 1 сервер с 1x NVIDIA L40S (48GB) или 2x RTX 4090 (24GB) обеспечивает пропускную способность до 15-25 запросов в минуту для модели Qwen2-VL-7B (квантование AWQ/GPTQ).
  - Учитывая, что в спорную зону попадает не более 2-5% от всех запланированных проверок отчетов, одного GPU-сервера достаточно для обслуживания пула из 10 000+ отчетов компании.

## 3. Ревизия существующего кода: выявленные баги, уязвимости и техдолг

В результате глубокого аудита кодовой базы (`src/pbimonitor`) выявлены следующие конкретные проблемы надежности, безопасности и архитектуры:

### 3.1. Безопасность и утечка учетных данных (Security)
1. **Передача паролей в открытом виде через URL (CWE-598):**
   - **Файл:** `src/pbimonitor/infrastructure/selenium/client.py`, метод `_build_auth_url` (строки 212–230).
   - **Проблема:** Метод собирает URL с учетными данными: `f"{username}:{password}@{parsed.hostname}"`. При вызове `driver.get(auth_url)` этот URL с незашифрованным паролем оседает в сетевых логах браузера, истории Chrome, логах прокси-серверов и отладочных сообщениях WebDriver.
   - **Решение:** Использовать безопасную передачу заголовков через DevTools Protocol (`execute_cdp_cmd('Network.setExtraHTTPHeaders')`) или интерактивную форму аутентификации.
2. **Отсутствие безопасного хранилища секретов:**
   - **Файл:** `src/pbimonitor/config/settings.py` (строки 69–71).
   - **Проблема:** Учетные данные `powerbi_username` и `powerbi_password` хранятся в открытом виде в переменных окружения / `.env`.
   - **Решение:** Поддержка интеграции с HashiCorp Vault, CyberArk или системными Secret Management сервисами (K8s Secrets).

### 3.2. Надежность браузерного движка и утечки ресурсов (Reliability & Leaks)
1. **Зомби-процессы Chrome и chromedriver при сбоях:**
   - **Файл:** `src/pbimonitor/infrastructure/selenium/client.py`, методы `close()` и `reauthenticate()` (строки 67–74, 100–107).
   - **Проблема:** При падении браузера или зависании WebDriver метод `self._driver.quit()` может упасть с `WebDriverException`. В блоке `finally` ссылка обнуляется (`self._driver = None`), но дочерние процессы `chrome` и `chromedriver` остаются в операционной системе как зомби-процессы, постепенно исчерпывая память и дескрипторы PID.
   - **Решение:** Внедрение процесса-надсмотрщика (process supervisor) с вызовом `kill_process_tree(pid)` и использование изолированных контейнеров Playwright / Chrome.
2. **Зависание на `time.sleep` и неблокирующее ожидание:**
   - **Файл:** `src/pbimonitor/infrastructure/selenium/client.py` (строка 84).
   - **Проблема:** `time.sleep(self._browser.page_load_wait_seconds)` жестко блокирует поток воркера на 10+ секунд, даже если отчет загрузился за 500 мс, либо прерывает рендер, если отчет рендерился 11 секунд.
   - **Решение:** Детерминированные промисы готовности и перехват сетевых событий через CDP (Chrome DevTools Protocol).

### 3.3. Логические ошибки и целостность данных (Concurrency & Logic Bugs)
1. **Race condition и повреждение файлов в `os_replace_safe`:**
   - **Файл:** `src/pbimonitor/application/usecases/check_report.py`, строки 143–146.
   - **Проблема:**
     ```python
     def os_replace_safe(current: Path, target: Path) -> None:
         if target.exists():
             target.unlink()
         current.replace(target)
     ```
     Удаление `target.unlink()` перед `replace` неатомарно. В многопоточном режиме или при параллельных проверках возникает окно гонки (Time-of-Check to Time-of-Use). Кроме того, `os.replace` в POSIX-системах уже является атомарной операцией и не требует ручного `unlink`. В случае сбоя между `unlink` и `replace` файл эталона полностью теряется.
   - **Решение:** Использовать стандартный атомарный вызов `os.replace(current, target)`.
2. **Гонка автопродвижения эталона (Baseline Drift Bug):**
   - **Файл:** `src/pbimonitor/application/usecases/check_report.py`, строки 99–102.
   - **Проблема:** При любом изменении (`diff_percent > 0`), статус становится `changed`, и код **тут же** заменяет `last_baseline.png` текущим скриншотом: `os_replace_safe(current, last_baseline)` и перезаписывает хеш в БД. Это означает, что сломанный отчет мгновенно становится новым эталоном для следующей итерации. Происходит так называемый «дрейф дефекта» (defect drift).
   - **Решение:** Эталон должен оставаться неизменным до явного подтверждения оператором через UI/API (`Baseline Approval Workflow`).

### 3.4. Ограничения базы данных и масштабирования (Database & Schema)
1. **Хранение тяжелых бинарных дельт (BYTEA) в строках OLTP-таблицы:**
   - **Файл:** `schema.sql` (строка 29), поле `delta_compressed BYTEA`.
   - **Проблема:** Хранение сжатых XOR-картинок прямо в таблице `monitoring_checks` приводит к взрывному раздуванию (bloat) таблицы и TOAST, деградации кеша страниц памяти PostgreSQL и замедлению регулярных запросов выборки статусов.
   - **Решение:** Перенос артефактов скриншотов и дельт в S3-совместимое объектное хранилище (MinIO / Ceph), а в БД — сохранение URI ссылок.
2. **Ненадежный поиск следующей задачи планировщиком:**
   - **Файл:** `src/pbimonitor/infrastructure/queue/scheduler.py`.
   - **Проблема:** Планировщик полностью работает в памяти текущего процесса (`queue.PriorityQueue`). При перезапуске контейнера или масштабировании до 2+ экземпляров задачи дублируются, теряются или рассинхронизируются.
   - **Решение:** Внедрение распределенной очереди (Celery / ARQ / Temporal / Redis Streams) с распределенными блокировками.

### 3.5. Тестовое покрытие (Testing Gaps)
- Интеграционные тесты `tests/integration/test_storage_integration.py` пропускаются при отсутствии переменной `TEST_DATABASE_DSN`.
- Полностью отсутствуют тесты на планировщик `InProcessScheduler` и обработку граничных состояний конкурентности.
- Отсутствуют тесты сквозного пайплайна `CheckReportUseCase` с имитацией ошибок Selenium.

## 6. Режим Semi-Realtime, масштабирование и управление нагрузкой

Переход от ночных проверок раз в сутки к quasi-realtime мониторингу (проверки каждые 1–5 минут для критических отчетов).

### 6.1. Пул браузеров повышенной производительности (Browser Warm Pool)
- Отказ от запуска нового процесса Chrome на каждую проверку (текущий overhead: 2–4 секунды на старт процесса).
- **Архитектура Warm Browser Pool на базе Playwright:**
  - Пул постоянно запущенных инстансов браузера в фоновом режиме.
  - На каждую задачу создается легкий изолированный контекст (`BrowserContext`) с очисткой кэша/кук за <100 мс.
  - Переиспользование предзагруженных шрифтов и базовых библиотек.

### 6.2. Событийная модель триггеров (Event-Driven Architecture)
Вместо постоянного «слепого» поллинга дашбордов внедряется гибридная схема:
- **Webhook API:** эндпоинт `/api/v1/trigger-check` для вызова из ETL/ELT-пайплайнов (Apache Airflow, Dagster, dbt Cloud, Cron). Как только витрина данных обновилась, ETL шлет сигнал на проверку визуала.
- **Kafka / RabbitMQ Consumer:** подписка на системные топики завершения обновления датасетов.

### 6.3. Приоритезация и защита BI от перегрузки (Rate Limiting & Backpressure)
- **Многоуровневая очередь задач (Priority Queue):**
  - `Priority 0 (P0)`: Триггеры обновления ETL, критичные дашборды топ-менеджмента.
  - `Priority 1 (P1)`: Регулярный semi-realtime мониторинг (интервал 5–15 мин).
  - `Priority 2 (P2)`: Периодический ночной аудит менее важных отчетов.
- **Защита аналитических систем (BI Throttling):**
  - Ограничение максимального количества одновременных сессий рендеринга к одному BI-кластеру (например, не более 5 конкурентных запросов к одному инстансу Visiology/DataLens во избежание деградации для реальных пользователей).
  - Умный адаптивный Backpressure: при росте задержки рендеринга интервалы проверок динамически увеличиваются.

### 6.4. Оценка аппаратных ресурсов (Resource Sizing Guide)

Расчет для инфраструктуры на **1 000 отчетов** с проверкой каждые **15 минут** (~66 проверок в минуту / ~1.1 проверки в секунду):
- **Рендеринг (Playwright/Chrome):**
  - Среднее время рендера отчета: 4 секунды.
  - Необходимое число параллельных браузерных контекстов: $1.1 \times 4 \approx 5$ активных сессий.
  - Рекомендуемый запас (пик x3): 15 параллельных браузерных воркеров.
  - Требуемые ресурсы: 8–12 vCPU, 24–32 GB RAM.
- **Хранилище данных (PostgreSQL + MinIO S3):**
  - Скриншоты сохраняются только при изменениях или ошибках; для неизменных отчетов сохраняется только метаинформация.
  - При 5% частоте изменений: 50 снимков в час $\approx$ 1 200 снимков в сутки.
  - Средний размер оптимизированного PNG/WebP: 300 КБ.
  - Прирост хранилища S3: ~360 МБ/сутки $\approx$ ~11 ГБ/месяц (с учетом дедупликации и сжатия).

  - Обеспечение нативной сборки, тестирования и подтвержденной совместимости с:
    - **Astra Linux Special Edition** (релиз «Смоленск» / «Воронеж» 1.7+);
    - **РЕД ОС** 7.3 / 8;
    - **Альт Линукс** (Альт СП, Альт Сервер 10).
- **Системы управления базами данных:**
  - Полная совместимость и поддержка сертифицированных отечественных СУБД:
    - **Postgres Pro Standard / Enterprise** (версии 14, 15, 16);
    - Отказ от специфических расширений, отсутствующих в сертифицированных сборках Postgres Pro.

### 7.4. Требования к документации, локализации и правообладателю
- **Язык интерфейса и документации:**
  - Все экраны веб-интерфейса, системные сообщения, журнал событий и документация должны быть полностью на русском языке (допускается наличие мультиязычности).
  - Подготовка комплекта документов по ГОСТ (ГОСТ 19 и ГОСТ 34): «Руководство системного программиста», «Руководство оператора», «Описание программы», «Технические условия».
- **Правообладатель:**
  - Исключительные права на программное обеспечение должны принадлежать коммерческой организации с российским бенефициарным владением (>50%) или гражданину РФ.
  - Подтверждение отсутствия зарубежных отчислений роялти за ключевые компоненты (>30% от выручки).

## 8. Поэтапный план реализации (Phased Implementation Plan)

План разбит на 5 ключевых этапов с оценкой инженерной трудоемкости и зависимостями.

### Этап 1: Рефакторинг ядра, устранение техдолга и контракт адаптеров
*Фокус: стабилизация, безопасность, переход к универсальной архитектуре.*
- **Задачи:**
  1. Устранение уязвимости передачи пароля в URL (`src/pbimonitor/infrastructure/selenium/client.py`).
  2. Исправление гонки в `os_replace_safe` и отмена автоперезаписи эталона при `changed` (`check_report.py`).
  3. Удаление внешней сетевой зависимости `webdriver-manager`.
  4. Проектирование и внедрение интерфейса `BaseBIAdapter`.
  5. Рефакторинг существующей логики Power BI в адаптер `PowerBIAdapter`.
  6. Расширение интеграционных тестов с изоляцией в Docker.
- **Трудоемкость:** 4–6 инженерных человеко-недель.
- **Ключевой результат:** Ядро системы абстрагировано от конкретного BI; закрыты критические проблемы безопасности.

### Этап 2: Адаптеры отечественных и Open Source BI-систем
*Фокус: расширение поддерживаемых платформ.*
- **Задачи:**
  1. Реализация P0 адаптеров: **Yandex DataLens** и **Visiology 3.x**.
  2. Реализация Open Source адаптеров: **Apache Superset** и **Metabase**.
  3. Разработка механизма ожидания `networkidle` и интеграция с Playwright как альтернативным сверхбыстрым движком рендера.
  4. Поддержка специфических селекторов и маркеров готовности для каждой системы.
- **Трудоемкость:** 6–8 инженерных человеко-недель.
- **Ключевой результат:** Система способна параллельно мониторить разнородный парк дашбордов (DataLens + Visiology + Superset + Power BI).

### Этап 3: Продвинутый алгоритмический diff и интеграция локального VLM-слоя
*Фокус: точность детекции и сведение к нулю ложных срабатываний.*
- **Задачи:**
  1. Внедрение покомпонентного сравнения (Visual-level diffing) и маскирования (статические зоны + CSS-селекторы).
  2. Переход на SSIM/MS-SSIM алгоритмы анализа изображений.
  3. Интеграция OCR-модуля для верификации числовых значений KPI.
  4. Развертывание шлюза локального инференса VLM (vLLM / Triton) с моделью `Qwen2-VL-7B`.
  5. Реализация структурированного JSON-протокола арбитража спорных инцидентов.
- **Трудоемкость:** 6–8 инженерных человеко-недель.
- **Ключевой результат:** Снижение False Positive срабатываний на 90%+; интеллектуальные вердикты на русском языке.

### Этап 4: Корпоративный веб-интерфейс, SSO и распределенная очередь
*Фокус: переход к продуктовому веб-решению enterprise-класса.*
- **Задачи:**
  1. Разработка FastAPI бэкенда с вынесением конфигурации отчетов из JSON в базу данных PostgreSQL.
  2. Реализация SPA веб-интерфейса (React/Vite/Tailwind): каталог, дашборды, визуальный инспектор шторкой.
  3. Разработка визуального редактора масок на скриншоте отчета.
  4. Внедрение механизма ручного согласования эталонов (Approval Flow).
  5. Перевод очередей на распределенную архитектуру (Redis/Celery/ARQ).
  6. Интеграция корпоративного SSO (Keycloak, OpenID Connect, LDAP).
- **Трудоемкость:** 8–10 инженерных человеко-недель.
- **Ключевой результат:** Полнофункциональный веб-сервис с разграничением прав (RBAC) и удобным UI для аналитиков и руководства.

### Этап 5: Наблюдаемость, Semi-Realtime и подготовка к Реестру Минцифры
*Фокус: интеграция в корпоративный ИТ-ландшафт и регуляторное соответствие.*
- **Задачи:**
  1. Полноценный Prometheus-экспортер метрик и эталонные дашборды Grafana.
  2. Реализация шаблонов Zabbix и двусторонней интеграции с Jira/YouTrack/Telegram.
  3. Оптимизация пула браузеров (Playwright Warm Pool) и вебхуки интеграции с ETL (Airflow).
  4. Тестирование и адаптация под Astra Linux, РЕД ОС и СУБД Postgres Pro.
  5. Подготовка комплекта технической и эксплуатационной документации по стандартам Минцифры.
- **Трудоемкость:** 6–8 инженерных человеко-недель.
- **Ключевой результат:** Готовый коробочный продукт enterprise-уровня, включенный в Реестр отечественного ПО.
